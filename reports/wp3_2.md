# WP3.2: encoding versus BREC distinguishability

This controlled comparison measures realized GIN pair distinguishability with
RWSE (return probabilities at steps 1 through 16) and LapPE (`k=1,2,4,8,16`,
`eigen_tol=1e-8`). Seeds default to 0–4: six conditions, 30 full runs.
The experiment specification is `analysis/wp3_2.py:matrix`, combined with the
existing `configs/models/gin.yaml`, `configs/tasks/brec.yaml`, and encoding YAMLs.
Only LapPE `k` is overridden. There is no per-condition hyperparameter tuning.
The same GIN, BREC loader, seeded evaluator, RPC decision and reliability tests
used by WP3.1 are reused without changes.

From the repository root, with the project environment activated:

```powershell
python scripts/reproduce_wp3_2_pe_variants.py --encoding rwse --seed 0
python scripts/reproduce_wp3_2_pe_variants.py --encoding lappe --k 8 --seed 0
python scripts/reproduce_wp3_2_pe_variants.py --all --seeds 0 1 2 3 4 --resume
python scripts/analyze_wp3_2_pe_variants.py --baseline-dir results/runs
```

Use `--results-dir` to select raw storage (default `results/wp3_2/runs`) and
analysis `--output-dir` to select tables (default `results/wp3_2/analysis`).
The runner also accepts `--output-dir` as an alias. `--threads` defaults to one.
`--encoding lappe` without `--k` runs all five dimensions. Arbitrary positive
dimensions and nonnegative NumPy-compatible integer seeds are supported.

Existing files are never overwritten. `--resume` checks the complete run,
configuration and configured embedding arrays before skipping it; even a completed
run with reliability failures is reused, avoiding selective reruns. Interrupted
runs are not resumed at pair level. If an orphan embedding or malformed result
exists, preserve it and use a new output directory. Analysis also refuses overwrite.

Raw JSON retains the full evaluator schema: seed, encoding configuration,
hyperparameters, source hash, protocol, timestamp, commit, environment, runtime,
parameter count, completion/validity flags, and each pair's ID, category, epochs,
loss, test/reliability statistics and decision. NPZ stores the evaluator embeddings.
LapPE filenames include `_kN` to avoid dimension collisions. Outputs remain under
the repository's ignored `results/` tree; no generated benchmark data is committed.

Analysis writes:

- `wp3_2_by_seed.csv`: counts, fractions, pair totals and validity per seed.
- `wp3_2_encoding_summary.csv`: mean, sample SD (`ddof=1`), minimum, maximum,
  exact seeds and reliability status per condition, including the optional saved
  vanilla GIN reference. Baseline values are read, never hard-coded.
- `wp3_2_lappe_curve.csv`: the LapPE rows, sorted by numeric `k`, with both count
  and fraction means and SD. Plot `k` against `mean_distinguished` or `mean_fraction`.

By default, every requested run must exist and be complete. For a single condition,
pass analysis `--encoding lappe --k 8 --seeds 0` (or `--encoding rwse`).
`--allow-missing` reports absent files and summarizes available full runs; it never
accepts incomplete JSON runs. Consult each row's seed list before comparing partial
curves. SD is blank for a single seed. Incompatible dataset hashes, models, training,
protocols or within-condition encoding settings are rejected.

The count includes only pairs passing the existing test AND reliability decision.
A full run with any reliability failure still has no valid primary benchmark score;
diagnostic counts remain in the tables with `all_benchmarks_valid=False` and failure
totals. Do not interpret such rows as valid benchmark improvements.

LapPE appends exactly `k` features and zero-pads unavailable positive-eigenvalue
directions; the requested dimension is retained even for small/disconnected graphs.
Existing sign anchoring does not resolve repeated-eigenvalue basis ambiguity.
Reliability results therefore matter particularly for LapPE. Input width and hence
parameter count vary with encoding. Seeds reproduce the repository's existing RNG
convention; bitwise agreement across devices/software versions is not guaranteed.

The implementation tests use synthetic results and do not execute the expensive
30-run benchmark. Measured curves require completing the commands above; no claim
of improved expressivity is made from implementation tests.
