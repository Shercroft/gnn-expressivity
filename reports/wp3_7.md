# WP3.7: expressivity–cost table

This analysis combines realized BREC distinction and recorded resource cost.
It reads finalized full results; it neither trains models nor changes architecture,
training, optimizer, positional encodings, RPC thresholds or reliability rules.
It does not rank theoretical expressivity or declare a universally fastest model.

## Telemetry audit

Inspected WP3.1–WP3.3 saved JSON, WP3.2/WP3.3 reports, GraphGPS runtime/recovery
documentation, evaluator, `training/profiling.py`, parameter-count logic,
environment metadata, dependencies and WP3.5/WP3.6 analysis infrastructure.
All eight available default-seed full runs have all four phase/run timing totals,
trainable parameter count, final-process RSS, environment metadata and per-pair
epochs. GraphGPS LapPE k=4 seed 0 additionally has all 400 pair elapsed times.
GIN none seeds 0–4, GIN degree seed 0 and GIN LapPE k=4 seed 0 lack pair durations.

The existing `Timer` uses `perf_counter` and synchronizes CUDA/MPS at block
boundaries. `count_parameters` counts parameters with `requires_grad=True`.
The evaluator verifies this count is constant across pairs. WP3.7 verifies
consistency across seeds for each exact configuration, even across environments.
Different encodings/k may legitimately change input width and parameter count.

| Saved telemetry | WP3.7 field | Meaning / units |
|---|---|---|
| num_parameters | parameter_count | Trainable parameter count |
| evaluated_pairs | total_pairs | 400 for accepted full runs |
| preprocessing_time_sec | preprocessing_total_sec | Dataset setup/validation, encoding, batching and fresh model construction, seconds |
| training_time_sec | training_total_sec | Accumulated pair training, seconds |
| inference_time_sec | inference_total_sec | Test plus reliability embedding inference, seconds |
| evaluation_time_sec | wall_clock_total_sec | Recorded evaluation elapsed time, seconds; resumed-run limitations below |
| pairs[].pair_elapsed_sec | mean_pair_elapsed_sec | Mean only if all pairs have saved duration, seconds |
| pairs[].epochs | mean_pair_epochs | Mean only with complete saved epoch coverage |
| process_memory_mb | process_rss_snapshot_bytes | Final process RSS snapshot; historical “mb” means MiB, converted using 1024² |
| peak_gpu_memory_mb | peak_cuda_allocated_bytes | Existing framework CUDA allocated peak in MiB, converted to bytes; CUDA runs only |

Separate RPC/test durations and per-pair preprocessing/training/inference times
are not saved. GraphGPS phase messages print phase times but are not a structured
saved duration series; this analyzer does not reconstruct telemetry from logs.
`training_median_sec` is therefore NA. Subtracting phase totals from wall time
would combine RPC, logging, checkpointing and other overhead and is not used to
invent an RPC measurement.

## Memory availability and instrumentation

`process_memory_mb()` uses psutil, already a project dependency. It reports
current RSS at the end, **not peak CPU RSS**. That defensible historical snapshot
is reused and labelled explicitly; `peak_cpu_rss_bytes` stays NA for every run.
No tracemalloc estimate is substituted for native/PyTorch process memory.

The evaluator already uses `reset_peak_memory_stats` and `max_memory_allocated`
on CUDA runs. That is a framework allocated-memory peak since reset, not total
device usage or reserved memory. `peak_cuda_reserved_bytes` is NA because it was
not measured. On CPU/MPS, both CUDA peak columns are NA regardless of a stale
GPU-memory value in a result. All current runs are CPU-only, so no historical
CUDA peak is available.

Existing memory telemetry is reused; no new sampling or evaluator instrumentation
is introduced. Historical missing peaks cannot be recovered from the final RSS.
If future CPU peaks are needed, the smallest optional addition would be a psutil
RSS sampler with explicit interval and profiling metadata; CUDA reserved peaks
could use `max_memory_reserved`. Such future sampled CPU peaks would be estimates
and require overhead measurement. Neither option was needed to extract these
tables, and neither is silently enabled by this analyzer.

## Schema, derived metrics and validity

`wp3_7_resource_by_run.csv` has one row per accepted full result:

- Model, encoding, k, seed, run ID/path, commit, total pairs and parameter count.
- Preprocessing/training/inference totals and amortized means in seconds.
- Training median (NA), wall-clock total, measured mean pair elapsed (if available),
  total seconds per pair and mean epochs.
- RSS snapshot and CPU/CUDA peak columns in bytes, with memory-kind labels.
- Device, accelerator, OS, Python/PyTorch/PyG versions, Torch thread count,
  environment identity and JSON.
- Distinguished count/fraction, benchmark validity, reliability failures and
  optional distinguished pairs per recorded hour.
- Configuration and measurement identities with corresponding audit metadata.

Phase means divide the recorded total by the number of pairs. They are amortized
costs; preprocessing includes one-time setup. `total_sec_per_pair` divides wall
time by pair count and is not relabelled as measured pair elapsed time. A mean
pair elapsed value requires an actual saved duration for every pair.

`distinguished_pairs_per_hour = distinguished_count × 3600 / wall_clock_total_sec`
only for valid runs with positive measured duration. Zero distinguished pairs
gives zero throughput; missing/zero wall time gives NA. No time-per-distinguished
ratio or composite score is constructed. This is retrospective descriptive
throughput for the fixed benchmark, not a general model efficiency guarantee.

`wp3_7_expressivity_cost.csv` reports model/encoding/k, exact seeds, n_seeds,
valid seed list/count, valid-only distinguished mean/sample SD/fraction, failure
totals and validity. Every resource/derived metric has `mean_<metric>`,
`std_<metric>` and `n_<metric>` columns, with units retained in the name.
SD uses ddof=1 and is NA for fewer than two measurements. Missing metrics are
excluded from that metric's mean, never filled with zero; each denominator is
explicit. Entirely missing metrics have NA means and n=0.

Costs of invalid full runs remain diagnostic observations. Primary distinction
means include only valid runs; resource means include all contributing full runs.
`n_seeds`, `n_valid_seeds`, per-resource n, failure totals and validity make these
different denominators explicit. Never interpret a row with failures as a valid
expressivity improvement. Invalid runs have no throughput ratio.

`wp3_7_resource_audit.json` distinguishes absent results from present results
with unavailable metrics. It lists available/unavailable metrics per run,
recorded-versus-derived provenance, exact configuration definitions, resource
group coverage, missing seeds and skipped files.

## Environment and measurement compatibility

Grouping uses exact model/encoding/training/optimizer/task/source/protocol settings
(reusing existing signature conventions), environment identity, and measurement
identity. Different training variants remain separate. Seed/commit/path are not
configuration knobs. Parameter count is validated rather than used to hide a
within-configuration mismatch in a different group. Saved category membership
must agree globally; WP3.5 validation handles full-run decisions and summaries.

Environment groups include device, accelerator, OS, Python, Torch, PyG and Torch
thread count. Incomplete environment information forces per-run groups rather
than treating two unknown environments as proven compatible. Timing/memory
numbers from different recorded environments are never silently pooled.
CPU model, physical RAM, power settings, thermal state and competing load were
not recorded historically: matching metadata is necessary, not sufficient proof
of equivalent hardware or experimental conditions.

Measurement groups retain pair-timing coverage (absent/partial/complete), explicit
`resource_profile` metadata if supplied, RSS availability and environment gaps.
This separates recorded diagnostic/profile coverage. Absent profile metadata
means “not recorded”, not proof of profiling being disabled. Overhead was not
quantified historically. GraphGPS diagnostic/checkpoint I/O can affect wall time;
these figures must not be interpreted as overhead-free architecture comparisons.

Checkpoint resumes accumulate committed work plus the final session. Abandoned
work inside an interrupted pair and downtime are not included. Memory fields
describe the final process; CUDA peaks are not historical peaks over all sessions.
Phase totals need not sum exactly to wall time. Embedding publication and other
post-timer work may be outside recorded evaluation elapsed time.

## Commands and coverage

From the repository root:

```powershell
.\.venv\Scripts\python.exe scripts/analyze_wp3_7_resources.py --allow-missing
```

Outputs default to `results/wp3_7/analysis/`. The command above was executed
without training. Existing outputs are protected; select a fresh `--output-dir`
for another snapshot. Use `--results-dir`, `--seeds`, and repeated
`--condition MODEL:ENCODING[:K]` to select inputs, for example:

```powershell
.\.venv\Scripts\python.exe scripts/analyze_wp3_7_resources.py --allow-missing --condition gin:lappe:4 --seeds 0 1 2 3 4 --output-dir results/wp3_7/gin_lappe4
```

Defaults reuse the 13 WP3.1–WP3.3 conditions and seeds 0–4 (65 slots).
Eight full runs exist and 57 slots are missing. Without `--allow-missing`, gaps in
the requested matrix or observed resource groups cause failure. Missing resource
metrics remain NA even in strict mode: unavailable telemetry differs from an
absent run. Range, first-N/smoke, checkpoint and incomplete artifacts are excluded
and audited using WP3.5 discovery; malformed claimed full runs fail loudly.
