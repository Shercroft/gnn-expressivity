# WP3.6: realized-expressivity variability

BREC records what a trained implementation distinguishes under a specific
initialization, optimizer configuration and budget. This realized expressivity
does not establish the architecture's expressive power in principle. Variation
across seeds is not a change in theoretical expressive power; a failure to
distinguish a pair is not proof of theoretical inability.

## Reused evidence and identity

The analysis reuses WP3.5 full-run validation, discovery, global saved category
membership checks and category summaries, the existing experiment signature and
environment metadata fields, and WP3.2/WP3.3 planned condition matrices. No
evaluator, model, encoding, training configuration or benchmark rule is modified.

Saved JSON contains model/encoding/k, full config, seed, source hash, protocol,
environment, validity flags, per-pair category, epochs, decisions and reliability.
Current `training/brec_evaluation.py::train_pair` fixes Adam and stopping below
`LOSS_THRESHOLD=0.2`; `configs/tasks/brec.yaml` exposes maximum epochs, learning
rate, weight decay and task batch size. Actual per-pair epochs record realized
budget, not a separate intentionally chosen hyperparameter. The by-seed table
includes mean/max epochs and number of pairs reaching the configured epoch limit
when these records exist. Missing epoch records remain blank.

A scientific condition contains the **entire model and encoding configurations**.
This preserves GIN/GraphGPS, no PE/degree/RWSE/LapPE, LapPE k, attention settings,
hidden width, layers, dropout and encoding options as separate conditions.
Conservatively, all model-config options define the condition, even when they
could also be studied as regularization knobs in another experiment.

A training variant contains the full training config, task batch size and any
explicit config optimizer section. Seed is separate and is never hashed into a
variant. Full SHA-256 identifiers label canonical sorted JSON configurations;
the availability JSON provides their exact definitions. Optimizer options in
future recorded configs are preserved without claiming current runners expose
new optimizer knobs.

Within a condition, source hash, protocol (except deviation prose), task settings
except data_root/batch_size, parameter count and other scientific config sections
must match across both seeds and training variants. Unexpected differences fail
loudly. Duplicate condition/variant/seed entries fail rather than selecting a
preferred result. Saved pair-to-category mappings must match across **all runs**.
Labels are compared directly, never inferred from pair IDs.

Hardware/software/thread metadata does not create a training variant. Differences
produce console warnings and explicit environment-count/warning fields, including
comparisons across variants. Such comparisons may be confounded; these warnings
do not establish which environment differences affected the result. Metadata is
recorded by seed, and incomplete environment metadata is warned about.

## Commands and missing data

Run from the repository root with the project environment:

```powershell
.\.venv\Scripts\python.exe scripts/analyze_wp3_6_stability.py --allow-missing
```

Default input is `results`, output is `results/wp3_6/analysis`, and requested seeds
are 0–4. Outputs refuse overwrite; select a fresh `--output-dir` for a new snapshot.
To analyze just one condition or seed set:

```powershell
.\.venv\Scripts\python.exe scripts/analyze_wp3_6_stability.py --allow-missing --condition gin:lappe:4 --seeds 0 1 2 3 4 --output-dir results/wp3_6/gin_lappe4
```

Default expected conditions reuse WP3.1 none/degree, WP3.2 RWSE and LapPE
k=1,2,4,8,16, and WP3.3 none/RWSE and LapPE k=4,8,16. This is 13 conditions,
65 requested condition/seed slots. `--condition MODEL:ENCODING[:K]` can be repeated
to narrow the requested matrix. All matching architecture configurations and
recorded training variants remain separately identified.

Without `--allow-missing`, missing requested conditions or seeds within any
observed condition/training variant cause failure. With it, gaps are recorded,
never turned into zeros. The audit separates available seeds from valid seeds
and lists invalid seeds. Requested conditions absent entirely appear in the
discovery audit. No unobserved numerical hyperparameter grid is assumed.

Range/subset/checkpoint files are skipped and recorded by the reused discovery
helper. Malformed claimed full results fail validation. Only explicitly completed
400-pair runs with unique complete pair IDs enter analysis.

## Tables and metrics

All CSV files carry model, encoding, k, condition_id and hyperparameter_variant:

| File prefix `wp3_6_` | Contents |
|---|---|
| seed_variability.csv | Within-variant mean, sample SD, min/max count, fraction mean/SD, exact valid/available/missing/invalid seeds and validity |
| pair_stability.csv | Each pair's saved category, valid seed count/list, distinguished count/rate and descriptive classification |
| seed_agreement.csv | Every pair of valid seeds within a variant: intersection/union sizes and Jaccard similarity |
| category_variability.csv | WP3.5 summaries on valid seeds, separately by training variant and all six saved BREC categories |
| hyperparameter_by_seed.csv | Every full run, including invalid diagnostics, exact training/environment JSON, result path and epoch diagnostics |
| hyperparameter_summary.csv | Separate valid-seed statistics for each training variant; also useful when only a baseline variant exists |
| theory_vs_realized.csv | Exact architecture/encoding, conservative theoretical note, realized mean/SD, seed count and interpretation status |
| availability.json | Configuration catalogs, seed coverage, requested gaps, skipped files, environment warnings and hyperparameter comparison status |

Seed means and sample SD (`ddof=1`) never pool different training variants.
One valid seed gives blank SD and an explicit statement that seed stability is
not established. Zero valid seeds gives blank means/SD and no pair/agreement
rows. Fraction denominators are the full run size, or the actual category size
for category statistics. All six BREC categories are retained, including
`4-Vertex_Condition` and `Distance_Regular`.

With at least two valid seeds, pair labels are `always_distinguished`,
`never_distinguished` or `seed_sensitive`, defined by all, zero, or some valid
seeds distinguishing the pair. Each row includes n_seeds and the exact seed list.
One-seed pair rows instead use `insufficient_seeds`, while preserving the observed
rate. No claim is made about unseen seeds.

Jaccard is intersection/union of distinguished-pair sets. Two empty sets receive
1.0 by convention, with intersection=union=0 exposed. This is agreement on
distinguishing nothing, not evidence of high realized expressivity. Empty versus
nonempty sets gives zero. Agreement rows always name both seeds and n_seeds.

Complete runs with reliability failures remain in the by-seed diagnostics and
availability audit. They are excluded from means, SDs, pair rates, agreements and
category statistics. Overall summaries retain failure totals, invalid seed lists
and `all_benchmarks_valid=False` so this exclusion is explicit. Category summaries
describe only their valid contributing seeds; consult the overall/audit tables
for excluded runs. Invalid primary scores are never averaged with valid scores.

The theoretical-status column says `not established in this project` for these
exact encoded architectures. This avoids extrapolating a model-family statement
to every finite implementation or PE configuration. No beyond-1-WL claim is
inferred from BREC; WP3.4 remains blocked.

## Hyperparameter portion: DATA-BLOCKED

No alternative controlled training variants exist in available results. Tables
contain the baseline variant and the audit explicitly marks comparisons
DATA-BLOCKED. The implementation can compare recorded variants within an exact
condition. It identifies differing training fields and lists shared valid seeds
for every variant pair. A comparison is RUNNABLE only if at least one pair of
variants shares valid seeds; disjoint seed sets remain explicitly confounded.
RUNNABLE means a descriptive matched-seed comparison is possible, not that
environment differences or other limitations have been eliminated.

No numerical BREC hyperparameter grid was found in the inspected project configs
or reports. Proposed small controlled design, pending user/supervisor selection
of alternative values:

- Select one existing condition and hold architecture, encoding/k, source,
  protocol, environment and stopping rule fixed.
- Keep its documented baseline settings and vary **one** of learning rate,
  weight decay or maximum epochs at a time, using the existing evaluator knobs.
- Use the same already documented seed list 0–4 for each approved alternative.
  Prioritize completing baseline seed coverage before interpreting differences.
- Approve an alternative value and resource budget before generating/running
  new experiment configurations. Preserve each variant in a distinct result
  directory because existing run IDs do not encode training hyperparameters.

This report is the proposed design for approval; it invents no numerical values
and launches no sweep. Missing hyperparameter variants cannot be enumerated
numerically until that design is approved. No significance, causality or tuning
recommendation is inferred from the current incomplete matrix.

## Validation and limitations

Synthetic tests cover identities, seed lists, sample SD, single-seed handling,
pair rates/classification, Jaccard including empty sets, category reuse, global
membership, missing seeds, range/partial rejection, invalid diagnostics,
duplicates, incompatible metadata, training variants and environment warnings.
No unit test trains a BREC model.

```powershell
.\.venv\Scripts\python.exe -m pytest --basetemp=.tmp/wp3_6_final -o cache_dir=.tmp/wp3_6_cache -q
```

Full suite: **377 passed, 4 skipped**, with one existing Torch JIT deprecation
warning. Existing saved outcomes are
descriptive, conditional on the observed seeds and budgets. Model/config changes
are never interpreted as ordinary optimization variants. The analyzer validates
saved evidence; it does not recompute RPC statistics or establish theoretical
guarantees.
