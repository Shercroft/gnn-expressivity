# WP3.5 category analysis

The purpose is to locate realized BREC distinction within graph categories,
rather than interpret only an overall score. Analysis reads saved JSON; it does
not train models or change any scientific experiment semantics.

Inputs are WP3.1 GIN none (constant features)/degree, WP3.2 GIN RWSE/LapPE,
and WP3.3 GraphGPS none/RWSE/LapPE. Their shared evaluator schema stores
`pairs[].category`, `pair_id`, `distinguished`, `candidate_distinguished`, and
`reliable`, with `overall` and `by_category` summaries. No categories are inferred
from IDs by this analyzer. Counts and fractions are recomputed from saved pair
decisions, then reconciled with all saved summaries.

## Category schema

The request names four categories, but the repository's pinned BREC v3 metadata
has six. Dropping the final two would incorrectly make 360 pairs represent 400.
All six are therefore preserved in every table:

| Saved category label | Metadata pair IDs | Metadata size |
|---|---|---:|
| Basic | 0–59 | 60 |
| Regular | 60–159 | 100 |
| Extension | 160–259 | 100 |
| CFI | 260–359 | 100 |
| 4-Vertex_Condition | 360–379 | 20 |
| Distance_Regular | 380–399 | 20 |

These definitions come from `data/brec.py::CATEGORY_RANGES`. Analysis uses the
existing category vocabulary and benchmark total; category denominators come
from actual records, not hard-coded category sizes. Full runs require all 400
unique IDs, all six labels and explicit completion flags. The pair-to-category
mapping must agree across all runs, independent of model, encoding, k or seed.
This compares saved category metadata directly, without inferring labels from IDs.

## Commands

From the repository root, analyze currently available runs:

```powershell
.\.venv\Scripts\python.exe scripts/analyze_wp3_5_categories.py --allow-missing
```

The default output directory already contains the sample analysis. For another
snapshot, supply a fresh `--output-dir results/wp3_5/analysis_next`; existing
outputs are protected against overwrite. Default requested seeds are 0–4.
Use `--seeds` to explicitly request a different seed set.

To require the full WP3.2/WP3.3 matrix, explicitly declare its conditions. The
planned LapPE grids are k=1,2,4,8,16 for WP3.2 / GIN and k=4,8,16 for
WP3.3 / GraphGPS. The following command requests these grids plus none/RWSE:

```powershell
.\.venv\Scripts\python.exe scripts/analyze_wp3_5_categories.py --output-dir results/wp3_5/full_matrix --condition gin:none --condition gin:rwse --condition gin:lappe:1 --condition gin:lappe:2 --condition gin:lappe:4 --condition gin:lappe:8 --condition gin:lappe:16 --condition graphgps:none --condition graphgps:rwse --condition graphgps:lappe:4 --condition graphgps:lappe:8 --condition graphgps:lappe:16
```

Omit `gin:none` if considering WP3.2 alone. Add
`--condition gin:degree` to include the complete WP3.1 comparison. Without
`--allow-missing`, any absent requested condition/seed causes failure. With it,
the same command analyzes only available full runs and records every gap.

When no explicit conditions are requested, only observed conditions are audited;
the audit explicitly says unobserved conditions are unknown. Discovery never
asserts that the whole planned matrix exists based on observed conditions.

## Outputs and interpretation

All outputs are under `results/wp3_5/analysis/` by default:

- `wp3_5_by_seed_category.csv`: model, encoding, k, seed, category,
  distinguished_count, total_pairs, distinguished_fraction, benchmark_valid,
  reliability_failures, result_path.
- `wp3_5_category_summary.csv`: model/encoding/k/category, n_seeds, exact JSON
  seed list, mean/std/min/max distinguished count, mean/std fraction,
  category_pair_count, all_benchmarks_valid, total_reliability_failures.
- `wp3_5_category_comparison.csv`: wide mean counts by all six categories and
  Overall, with exact seeds, seed count, validity and reliability failures.
- `wp3_5_lappe_category_curves.csv`: LapPE subset of the long summary. Group by
  model/category and plot k against mean_fraction or mean_distinguished.
- `wp3_5_availability.json`: requested scope/seeds, available runs, missing
  condition/seed tuples, and skipped artifact paths/reasons.

Standard deviations use sample SD (ddof=1); one-seed SD is blank. Fractions
divide distinguished counts by the size of that category, so they can be
compared across differently sized categories. Overall wide counts sum all six
mean category counts. Every per-run total reconciles exactly before output.

Curves contain only observed k values. A single k is a point, not evidence of a
trend. Compare curves with their exact seed lists, SDs, and validity flags;
differing seed coverage can confound apparent changes with k. No figures or
new dependencies are necessary to consume these curve-ready CSVs.

## Validity and compatibility

Range/subset/checkpoint artifacts are excluded and reported. Malformed artifacts
claiming full completion fail loudly. Duplicate condition/seed runs also fail.
Full runs with reliability failures retain category diagnostics but remain
invalid for primary benchmark interpretation in both long and wide tables.
An invalid full run must have a null primary metric; its failure counts cannot
be hidden by aggregation. Invalid runs are included only with explicit validity
flags, consistent with the existing general BREC analysis convention.

Within each model/encoding/k condition, source hash, full model/encoding/training
config, task settings (excluding data_root), protocol (excluding deviation prose),
and parameter count must match across seeds. This reuses
the existing experiment-signature convention. Saved pair-to-category membership
must additionally match globally across all conditions and seeds. Different
conditions remain separate; the wide comparison does not establish that their training protocols
are controlled or their outcomes statistically different. Hardware and commit
differences alone do not define different scientific conditions.
